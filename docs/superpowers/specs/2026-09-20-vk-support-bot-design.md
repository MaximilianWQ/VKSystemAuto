# Бот поддержки ВК + веб-дашборд оператора — дизайн

Дата: 2026-09-20
Статус: утверждён

## Задача

Заменить существующий бот поддержки сообщества «Atlas Secure» (272 подписчика). Старый бот
работал через команды в ВК и имел четыре конкретные проблемы, видные на скриншотах:

| Проблема старого бота | Решение |
|---|---|
| `/close` без аргумента → «Нет активного чата. Укажите ID: /close 123456» | Кнопка «Закрыть» внутри открытого диалога. Понятие ID для оператора исчезает |
| Очередь обращений не видна — непонятно, кто ждёт и сколько | Левая колонка дашборда: все диалоги, непрочитанные, время ожидания, сортировка |
| Синтаксис `/chat 20763080` и `#169878016 текст` | Клик по диалогу и обычное поле ввода |
| Длинный `/help` с неочевидными командами | Команд нет. Только интерфейс |

## Границы

**Входит:** приём обращений в ВК, FAQ-меню с ответами из БД, передача оператору, веб-дашборд
оператора с реалтаймом, вложения в обе стороны, passkey-вход, PWA с пушами, статистика.

**Не входит:** несколько операторов и роли, массовые рассылки, теги и SLA-эскалации, интеграции
с CRM, голосовые и видео **от оператора** (входящие от клиента — показываем).

## Принятые решения

1. **Рабочее место оператора — веб-дашборд.** В ВК у оператора остаётся единственная команда
   `/link` для регистрации passkey. Команды `/chat`, `/close`, `/r`, `/tickets` не реализуем —
   именно они были источником боли.
2. **Оператор один** (он же админ, `ADMIN_ID`). Ни ролей, ни назначений, ни «взял в работу».
3. **Вход только по passkey (WebAuthn).** Паролей в системе нет.
4. **Один сервис на Railway** + Postgres. Без Redis.
5. **Домен** — стандартный `*.up.railway.app`. Переезд на свой домен предусмотрен через env.

## Архитектура

Один процесс FastAPI обслуживает четыре вещи:

```
POST /vk/callback      — вебхук Callback API
GET  /api/*            — REST дашборда
WS   /ws               — реалтайм в дашборд
GET  /*                — статика собранной PWA
```

Рядом — Postgres от Railway. Очередь отправки и рассылка событий в браузер внутрипроцессные:
при одном инстансе и одном операторе внешний брокер — лишняя сущность и лишние деньги.

Следствие, которое надо помнить: **горизонтально это не масштабируется.** Второй инстанс сломает
WebSocket-рассылку и заставит два воркера конкурировать за outbox. Если когда-нибудь понадобится
масштаб — переход на Postgres `LISTEN/NOTIFY` и `SELECT ... FOR UPDATE SKIP LOCKED`, но не сейчас.

### Поток данных

```
Клиент в ВК
   │
   ▼
VK Callback API ──POST──► /vk/callback
   │  1. сверка secret и group_id, иначе 403
   │  2. type=confirmation → отдать VK_CONFIRMATION_CODE текстом
   │  3. дедуп по event_id
   │  4. немедленно вернуть "ok", обработку — в фон
   ▼
Postgres: users / tickets / ticket_messages
   │
   ├─► WebSocket → дашборд открыт: сообщение появляется сразу
   └─► Web Push  → дашборд закрыт: пуш на iPhone или десктоп

Оператор отвечает в дашборде
   ▼
outbox ──воркер, 20 rps, ретраи──► messages.send
```

### Почему outbox, а не прямой вызов

Railway перезапускает процесс в любой момент — при деплое, при OOM, при миграции ноды. Прямой
`messages.send` из обработчика теряет ответ оператора при рестарте, и клиент просто не получает
сообщение. Поэтому любая исходящая отправка проходит три шага:

1. строка в таблицу `outbox` с **уже сгенерированным** `random_id`;
2. фоновый воркер забирает строки, шлёт с ограничением скорости, обрабатывает ошибки;
3. результат пишется обратно в строку.

`random_id` генерируется один раз при постановке в очередь и переиспользуется при всех ретраях.
ВК считает повтор с тем же `random_id` дублем и не доставляет его — это ровно то, что нужно:
ретрай после таймаута не породит второе сообщение у клиента.

Обработка ошибок VK API в воркере:

| Код | Значение | Поведение |
|---|---|---|
| 6 | Too many requests | Пауза, повтор с экспоненциальной задержкой |
| 9 | Flood control | Отложить надолго, не долбить |
| 901 | Сообщения запрещены | `can_write=false`, ретраи прекратить навсегда |
| прочие | — | Залогировать код и метод, ретрай до лимита попыток |

## Сценарий в ВК

Приветствие и главное меню кнопками. Темы FAQ и ответы лежат в таблице `faq` и редактируются
из дашборда — не из кода, иначе каждое изменение текста превращается в деплой.

| Кнопка | payload | Действие |
|---|---|---|
| Начать / Меню | `{"cmd":"menu"}` | Приветствие и меню |
| Частые вопросы | `{"cmd":"faq"}` | Темы inline-кнопками, ответ из `faq` |
| Написать оператору | `{"cmd":"ticket_new"}` | Создаёт обращение |
| Мои обращения | `{"cmd":"ticket_list"}` | Открытые обращения и статус |
| Закрыть обращение | `{"cmd":"ticket_close","id":N}` | Закрывает, просит оценку 1–5 |

Пока обращение открыто, любое сообщение клиента — включая вложения — падает в него автоматически.
Никаких команд от клиента не требуется.

Маршрутизация строго по `payload`, не по тексту кнопки: тексты будут меняться. Каждая команда
дополнительно работает текстом — у старых клиентов ВК клавиатуры может не быть.

Вне `WORK_HOURS` обращение создаётся как обычно, клиент получает автоответ с указанием, когда
ждать ответа.

## Вложения

### Входящие — показываем все типы

| Тип | Как отображаем |
|---|---|
| Фото | Галерея с лайтбоксом |
| Видео | Превью + штатный плеер ВК |
| Документы | Иконка типа, имя, размер, скачивание |
| Голосовые | Плеер с waveform и длительностью |
| Стикеры | Изображение |
| Геопозиция | Карта-превью со ссылкой |

Ссылки ВК на документы и голосовые подписаны и протухают, поэтому в браузер они не отдаются
напрямую. Эндпоинт `/api/attachments/{id}` стримит содержимое, а при 403 перезапрашивает свежий
URL через `messages.getById`. Прямых файлов видео VK API не отдаёт в принципе — отсюда плеер ВК
вместо своего.

### Исходящие — фото и файлы

`photos.getMessagesUploadServer` → POST → `photos.saveMessagesPhoto` для фото,
`docs.getMessagesUploadServer` → `docs.save` для файлов. Через аплоадеры vkbottle.

## Passkey

Библиотека `py_webauthn`. Регистрация первого ключа решается через самого бота, без временных
паролей в env: владелец `ADMIN_ID` пишет боту `/link`, бот отвечает одноразовой подписанной
ссылкой со сроком жизни 10 минут. Токен хранится хешем в `setup_tokens` и сгорает после
использования. Команда `/link` от кого угодно, кроме `ADMIN_ID`, игнорируется молча.

Схема даёт бесплатное восстановление: потерял телефон или сменил домен — пишешь `/link` и
регистрируешь ключ заново. Ключей можно держать несколько (телефон и ноутбук).

Сессия — серверная, идентификатор в HttpOnly + Secure + SameSite=Lax куке, отзывается удалением
строки. `WEBAUTHN_RP_ID` и `WEBAUTHN_ORIGIN` в env: при переезде на свой домен меняются, и ключи
регистрируются заново — passkey жёстко привязан к домену, это ограничение стандарта.

## PWA и пуши

Манифест `display: standalone`, иконки 192/512 и maskable, apple-touch-icon. Service worker
кеширует оболочку и принимает пуши. Отправка — `pywebpush` с VAPID-ключами из env.

Ограничения iOS, заложенные в интерфейс с самого начала:

- пуши работают только с iOS 16.4+;
- только если PWA добавлена на экран «Домой» — в обычной вкладке Safari их нет;
- `Notification.requestPermission()` обязан вызываться из обработчика нажатия;
- iOS периодически сбрасывает подписку, поэтому переподписываемся при каждом запуске.

Если приложение открыто не в standalone-режиме, показываем подсказку «Поделиться → На экран
Домой» вместо кнопки включения пушей, которая всё равно не сработает.

## Интерфейс

Визуальный язык по референсам: тёплый светло-серый фон, белые карточки радиусом ~28px с мягкими
тенями, крупные градиентные акценты (lime, coral, green) на числах статистики, тонкая типографика
с плотным трекингом на крупных цифрах, пружинные анимации и плавные layout-переходы. Светлая тема
основная, тёмная поддерживается.

Экраны:

- **Диалоги** — очередь и чат. Двухколоночно на десктопе, стек с навигацией назад на телефоне.
- **FAQ** — редактирование тем, ответов и порядка.
- **Статистика** — обращения за сутки и неделю, среднее время первого ответа, средняя оценка.
- **Настройки** — ключи passkey, пуши, рабочие часы.

Стек: React + TypeScript + Vite + Tailwind + Motion. Собирается в статику, отдаётся FastAPI.

## Схема БД

```
users(vk_id PK, first_name, last_name, photo_url, can_write, state,
      state_data jsonb, created_at, last_seen_at)

tickets(id PK, user_id FK, status open|in_progress|closed, rating,
        created_at, first_reply_at, closed_at, last_message_at, unread_count)

ticket_messages(id PK, ticket_id FK, direction in|out, text, attachments jsonb,
                vk_message_id, created_at, read_at)

faq(id PK, title, answer, position, is_active)

processed_events(event_id PK, created_at)          -- дедуп Callback API

outbox(id PK, peer_id, payload jsonb, random_id, attempts,
       next_attempt_at, status, last_error)

admin_credentials(id PK, credential_id bytea UNIQUE, public_key bytea,
                  sign_count, transports, name, created_at, last_used_at)

sessions(id PK, created_at, expires_at, user_agent)

push_subscriptions(id PK, endpoint UNIQUE, p256dh, auth, created_at, last_ok_at)

setup_tokens(token_hash PK, expires_at, used_at)
```

Индексы: `tickets(status, last_message_at)` для очереди, `ticket_messages(ticket_id, created_at)`
для ленты чата, `outbox(status, next_attempt_at)` для воркера, `processed_events(created_at)`
для чистки. `processed_events` чистится от записей старше суток.

## Тесты

**Модульные и интеграционные.** Каждый обработчик покрыт тестом уровня «событие ВК → какие вызовы
API ушли» с замоканным отправителем. Реальных запросов в ВК из тестов нет. Отдельно проверяются:
дедупликация событий, ретраи outbox по кодам 6/9/901, регистрация и проверка passkey, разбор
каждого типа вложения.

**Нагрузочные.** Реальный профиль — 272 подписчика и один оператор, но проверяем с запасом,
потому что Callback API умеет устраивать шторм повторов, и именно там ломаются такие системы.

| Сценарий | Нагрузка | Критерий приёмки |
|---|---|---|
| Шторм входящих событий | 500 событий/с, 30 с | p95 ответа вебхука < 100 мс, 0 потерянных, 0 обработанных дважды |
| Повторы Callback API | один `event_id` 10 раз подряд | обработан ровно один раз, ответ `ok` на все 10 |
| Пропускная способность outbox | 1000 сообщений в очереди | фактический темп не превышает 20 rps, очередь разгребается полностью, порядок в рамках одного диалога сохранён |
| Рестарт под нагрузкой | убить процесс с непустым outbox | после старта ни одно сообщение не потеряно и ни одно не отправлено дважды |
| WebSocket | 100 сообщений/с в открытый дашборд | без разрывов, задержка доставки < 200 мс |
| Пул Postgres | все сценарии выше | пул не исчерпан, нет ожиданий соединения дольше 1 с |

Инструмент — `locust` для HTTP-сценариев и asyncio-скрипты для outbox и WebSocket. Прогон против
локального стенда с поднятым Postgres и замоканным VK API.

## Definition of done

1. `pytest` зелёный
2. `ruff check` без ошибок
3. Нагрузочные сценарии проходят по критериям выше
4. Бот стартует локально с `VK_MODE=longpoll`
5. `npm run build` без ошибок и предупреждений TypeScript
6. Список переменных окружения для Railway выдан пользователю
